# MVP scope and release boundaries

## Must deliver

- Account-free PTO onboarding and an explained, accurate recommendation; US federal baseline with employer-confirmed days off first.
- Authenticated trip ownership and a focused personal dashboard.
- Secure invitations, mobile browser guest responses, and validated iOS linking.
- Private availability/PTO constraints and optional private budgets; visible participation progress.
- Explainable, fair group options, including unknown respondents and explicit compromises.
- Voting, pending leave approval, participation confirmation, organizer confirmation, and calendar sharing.
- Accessible product states, privacy-conscious events, monitoring before public beta, security review, and a TestFlight path.

## Explicitly deferred

Trip Capsules/photos (1.1), travel passport (1.2), open trips and stranger matching (2), points/rewards/expense optimization (3), payments, advertising, commercial booking APIs, AI agents, and irregular work shifts. No photo storage or speculative tables in the foundation. Do not create production resources or paid subscriptions automatically.

## Current execution boundary

Initialization establishes Phase 0 documentation, specialist roles, architecture and safe local tooling, followed by a minimal Expo welcome/navigation scaffold and checks. The PTO slice is planned in [the first sprint](../../plans/first-pto-sprint.md), not implemented as part of documentation creation. A welcome scaffold is not a working PTO product or an iOS-verified release.

## Scope control

The founder owns business scope and release acceptance. Record proposed changes in the backlog and their dependencies before implementation. A smaller supported calendar surface must be labeled honestly rather than implying worldwide holiday accuracy. When GitHub Issues is enabled, migrate active work there and leave this backlog as an index/archive to prevent contradictory statuses.
